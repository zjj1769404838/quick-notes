**存储路径以 `04-数据模型文档.md` 为权威**，本文全部引用其结论（v1 定稿）：

```
%APPDATA%\QuickNotes\                       ← Roaming：小体积、可备份
├─ config.json                              < 32KB；字段见 04 §7
├─ index\<rootHash>\search-index.json       rootHash = sha1(规范化小写 ROOT)[:12]
│                    vectors.bin            定长 768×Float32=3072B/条 + 16B 文件头
│                    vectors.meta.json
├─ logs\main-YYYYMMDD.log                   约 0.5MB/天，7 天轮转
└─ drafts\<sha1(相对路径)[:16]>.json        崩溃草稿，≤50 份，唯一含正文的临时件

%LOCALAPPDATA%\QuickNotes\models\           ← Local：不宜漫游（域环境会同步 1.3GB）
├─ models.lock.json                         基准清单（构建期由 resources\ 复制，只读）
└─ <modelId>\<下游原始文件名>.gguf + verify.json    （一模型一目录，文件名保留下游原名）
```

`models` 放 `%LOCALAPPDATA%` 而非 `%APPDATA%`：Roaming 在域环境会同步到服务器，1.3GB 会拖垮登录。索引按 `<rootHash>` 分命名空间正是 FR-5.9「只切索引不搬文件」的落地点——切回旧目录直接复用，保留最近 3 套（`builtAt` LRU）。

三条不可违反的架构约束：

1. **渲染进程无特权**：`sandbox:true` + `contextIsolation:true` + 无 `nodeIntegration`，所有能力经 preload 一事一接口（NFR-3）。
2. **主进程不阻塞**：任何 >16ms 的同步工作（索引构建、模型推理、大文件哈希）必须在 Worker 线程，主进程只做编排与窗口操作。
3. **笔记目录是唯一事实源**：任何索引、缓存、设置都可由笔记目录重建；删除己方数据不得影响笔记。

### 1.2 职责边界

| 层 | 唯一职责 | 禁止事项 |
|---|---|---|
| **主进程** | 窗口与屏幕几何、托盘/热键、单实例、文件 IO、索引与 AI 的**编排**、系统能力（open-path、协议注册）、日志落盘 | 不做分词、不跑推理、不做 Markdown 渲染、不持有 UI 状态 |
| **preload** | 把 IPC 通道封装成**类型化、按命名空间分组**的 API；注入 `window.qn`；校验事件订阅生命周期 | 不暴露 `ipcRenderer` 本体、不暴露 `require`/`process`、不实现业务逻辑、不拼路径 |
| **球渲染进程** | 画球、悬停透明度过渡、拖动指针捕获、右键菜单触发 | 不读文件、不持有笔记数据、不加载 React |
| **面板渲染进程** | 编辑器、预览、目录树、搜索、标签、设置、AI 浮层；所有状态为可重建的派生状态 | 不做 `fs`、不拼绝对路径、不信任任何内容（预览必过 DOMPurify） |
| **Index Worker** | 分词、倒排构建、增量维护、索引序列化/反序列化、embedding 近邻计算 | 不做 IO 之外的决策、不直接回渲染进程（只回主进程） |
| **AI Worker** | 模型生命周期、推理、流式 token、embedding | 不碰窗口、不写笔记文件 |

**为什么这样切**：把「几何 + 系统集成」留在主进程（Electron 只允许主进程做这些）；把「CPU 密集」下沉到 Worker（守住 NFR-1 冷启动与 FR-1.2「拖动无延迟跟手」的硬指标——推理一旦在主进程跑，`setBounds` 会掉帧）；把「内容与状态」全放渲染进程（笔记是文件的投影，可随时重读重建）。

## 3. 进程边界与安全配置

### 3.1 BrowserWindow 全参数

两个窗口都由 `window-factory.ts` 构造，共用安全基线，差异集中在窗口语义。

## 4. IPC 契约表

约定：通道名 `qn:<域>:<动作>`，常量集中在 `shared/ipc-channels.ts`；所有 `invoke` 返回 `Result<T, QnError>`，**不抛异常**（避免 Electron 序列化丢栈）；流式一律「invoke 拿 requestId → 事件通道增量推送」，不用 `MessageChannelMain`（面板窗口生命周期短，端口管理成本高于收益）。

错误码字典：`QN_E_BAD_REQUEST`（入参非法）/`QN_E_PATH_OUTSIDE_ROOT`（越容器）/`QN_E_NOT_FOUND`/`QN_E_NAME_CONFLICT`（重名）/`QN_E_IO`/`QN_E_FILE_LOCKED`/`QN_E_HASH_CONFLICT`（外部改动）/`QN_E_INDEX_BUILDING`/`QN_E_AI_DISABLED`/`QN_E_MODEL_MISSING`/`QN_E_MODEL_HASH`/`QN_E_AI_BUSY`/`QN_E_AI_TIMEOUT`/`QN_E_CANCELLED`/`QN_E_PERMISSION`/`QN_E_UNSUPPORTED`。

## 5. 分层设计（主进程内）

依赖方向**单向向下**，禁止反向 import（用 ESLint `no-restricted-imports` 固化）：

```
ipc/handlers ──→ services ──→ core
windows ──────→ services（仅 settings、notes 只读）────→ core
shell ────────→ services（仅 settings）───────────────→ core
bootstrap ────→ 全部（唯一允许做装配的地方）
core ─────────→ 无（只依赖 node: 内置）
```

**为什么这样切**：`ipc/` 会因为「契约变更」而改，`services/` 因为「业务规则变更」而改，`core/` 几乎不改。若把 `ipcMain.handle` 直接写在服务里，服务就被 Electron 绑死、无法在 Node 单测里跑（本项目要求核心服务可在 `node --test` 下无 Electron 运行）。

## 7. AI 子系统设计

### 7.1 结论：推理放 AI Worker 线程

**结论：node-llama-cpp 跑在 `worker_threads` 的 Worker 里，主进程只保留门面。** 四条理由按重要性排序：

1. **不能阻塞事件循环**：`llama.loadModel` 与 `evaluate` 大量时间在原生同步调用内，主进程一旦被占，`setBounds`/`moveTop` 会排队 —— 直接违反 FR-1.2「拖动无延迟跟手」与 FR-1.3 悬停过渡。
2. **崩溃隔离**：老 CPU 的 `illegal instruction`、Intel 核显 Vulkan 崩溃是**进程级致命**（需求 §6 风险表已列）。在 Worker 里崩，主进程 `worker.on('error')` 可捕获 → `terminate()` → 内存回收 → 置灰 AI 并提示，笔记功能毫发无损（FR-7.9 / NFR-1 不受影响）。
3. **可回收内存**：Worker 被 `terminate()` 后堆整块归还，满足 NFR-2「关闭 AI 后不占内存」；主进程内加载的模型无法可靠卸载。
4. **可换实现**：将来若 DLL 缺失需降级 llama-server sidecar，只改 `ai-worker.ts` 内部，IPC 契约不变。

代价与对策：跨线程传输 token 有序列化开销 → 用 `postMessage` 批量（每 8 token 或 24ms 合帧一次），而不是每 token 一次；Worker 内不允许 `require('electron')`（无该模块），故配置与路径一律经首帧 `init` 消息注入。

```ts
// services/ai/worker-protocol.ts
type MainToWorker =
  | { t: 'init'; modelsDir: string; tier: '0.6b' | '1.5b'; gpu: boolean; threads: number }
  | { t: 'load'; modelId: string; ctxSize: number }
  | { t: 'generate'; requestId: string; task: 'polish' | 'continue' | 'title'; prompt: string; params: GenParams }
  | { t: 'abort'; requestId: string }
  | { t: 'embed'; requestId: string; text: string }
  | { t: 'unload' }
  | { t: 'shutdown' };
type WorkerToMain =
  | { t: 'ready'; info: { modelId: string; backend: 'cpu' | 'vulkan'; ctx: number } }
  | { t: 'chunk'; requestId: string; delta: string }
  | { t: 'done'; requestId: string; tokens: number; ms: number; tokPerSec: number }
  | { t: 'embed-done'; requestId: string; vector: Float32Array }
  | { t: 'error'; requestId?: string; code: QnErrorCode; message: string; fatal: boolean }
  | { t: 'log'; level: LogLevel; msg: string };
```

### 7.2 模型生命周期

| 状态 | 触发 | 动作 | 退出条件 |
|---|---|---|---|
| `unloaded` | 启动 / 关闭 AI / 闲置卸载 | 无模型句柄 | 首个 AI 请求 |
| `loading` | 请求到达或用户点「启用 AI」 | Worker `init`+`load`；发 `ai:status{state:'loading'}` | `ready` 或 `error`（3s 无响应→`QN_E_AI_TIMEOUT`） |
| `ready` | `load` 成功，记录 `tokPerSec` 基线 | 单并发队列处理任务 | 闲置 5min / 切档 / 关闭 |
| `error` | 加载失败或 `fatal` | `terminate()` Worker，`ai.enabled=false` 持久化，`sys:fatal` 事件 | 用户手动重试 |

规则：**全进程同一时刻只有一个生成会话**（`QN_E_AI_BUSY` 排队而非并发），因为 0.6B 在 8GB 机器上并发会让 `mmap` 抖动；embedding 与生成共用同一 Worker 但**不同模型**，切换需先 unload 再 load（20MB 级 embedding 模型加载 <200ms，可接受）。

```

├─ models.lock.json                 基准清单（构建期由 resources\models.lock.json 复制，只读）
```

校验铁律（对齐 04 §10.3）：① **先比 size**，不符立即退出（不必算完哈希）；② 流式 sha256（0.6B 约 1–2s、1.5B 约 4s）与 `models.lock.json` 比对；③ 通过才写 `verify.json` 并 `rename` 落位（原子）；④ **校验失败必删**（网络中断保留 `.part` 供断点续传），写 `ai.lastError = {code:"E_HASH_MISMATCH", at, stage:"verify"}`，UI 给可读原因 + 手动放置路径 + 期望字节数 + 重试；同模型连续失败 2 次后不再自动重试（可手动触发）。启动时 `verify.json` 缺失或更旧于 gguf → 后台重校验（不阻塞启动），不过则视为缺失、置灰 AI 入口并给原因。

### 7.6 embedding 索引与 MiniSearch 索引并存

两套索引**同一生命周期、同一文档 id、不同存储**，互不替代：

| 维度 | MiniSearch（词法） | 向量索引（语义） |
|---|---|---|
| 位置 | `%APPDATA%\QuickNotes\index\<rootHash>\search-index.json` | 同目录 `vectors.bin` + `vectors.meta.json` |
| 体积 | 约 4.45MB / 1000 篇 | 3000 chunk × 3072B ≈ 9.2MB + 元数据 0.3MB |
| 内存 | Index Worker 堆内常驻 | Worker 堆内 `Float32Array` 常驻 + 按需 `mmap` 读取 |
| 失效 | mtime 变化 → 该 doc upsert | 同左 + 模型档位变更 → **全量重算**（向量空间不可混） |
| 查询 | `search(text)` <1ms | `embedQuery` (≈40ms) + 余弦 TopK（N=1000 时 <2ms） |
| 不可用 | 几乎不 | 模型缺失/AI 关闭 → `degraded:'no-embedding'` |

融合策略：`mode:"hybrid"` 时两路各取 Top20，用 **RRF（k=60）** 合并——不依赖两路分数量纲（MiniSearch 的 BM25 与余弦不可直接相加）；余弦相似度低于 `ai.semanticThreshold`（默认 0.62）的语义命中直接丢弃，避免弱相关污染。`vectors.bin` 为定长记录 `768×Float32=3072B` + 16B 文件头（magic `QNV1`/维度/chunk 数/版本），顺序与 `vectors.meta.json` 的 `chunks[]` 一一对应，后者记 `{docId, chunkIdx, startLine, endLine, mtime, modelId}`，`modelId` 用于判定向量可否复用（档位变更 → 全量重算）。

## 8. 并发与状态

### 8.1 自动保存：防抖 + 写盘竞态

- **防抖**：停止输入 800ms 触发（FR-3.5）；`maxWait 5000ms` —— 连续敲字 5s 必落盘一次，防「一直打一直不存」。
- **串行化**：`NoteWriter` 维护 `Map<noteId, Promise>` 链，同文件写入串行、不同文件并行；链上任务带序号，**旧序号写完成后若已有更新序号入队，不再回写旧内容**（防止慢写覆盖新写）。
- **原子写**：同目录写 `.qn-tmp-<pid>-<rand>` → `fh.sync()` → `fs.rename`（Windows 上 `MoveFileEx` 语义为替换）→ 目录 `fsync` 可选。任何步骤失败都保留原文件，返回 `QN_E_IO`/`QN_E_FILE_LOCKED`（杀软/索引器占用时重试 3 次，退避 120/360/900ms）。
- **冲突检测**：`save` 带 `baseHash`（上次读/写后的内容哈希）。若磁盘当前 hash ≠ `baseHash` 且内容确实不同，返回 `QN_E_HASH_CONFLICT` 并附 `diskHash/diskMtime`，前端弹三选：**重新加载（丢本地）/ 覆盖磁盘 / 另存副本**。默认高亮「另存副本」——不静默丢数据（NFR-4）。
- **退出兜底**：`before-quit` 调 `flushAll(2000)`，超时则把未落盘内容写进 `drafts/` 并在下次启动提示。

### 8.2 文件监听 vs 用户编辑

```
chokidar(4.0.3, awaitWriteFinish:{stabilityThreshold:200, pollInterval:50})
   │ change/add/unlink
   ├─ echo-suppressor: recentWrites 中该 path 的 {hash, mtime} 与事件
   │   mtime 相同且 1.5s 内 → 判定为自写回声 → 丢弃
   ├─ 命中「当前打开的文件」：
   │    编辑器无脏数据 → 静默提示 + 自动 reload（仅当 hash 变化）
   │    编辑器有脏数据 → 只显示横幅「文件已在外部变更」，绝不自动覆盖
   └─ 其它文件 → 合并 300ms → evt:notes:tree-invalidated（批量，不逐条刷 UI）
```

`awaitWriteFinish` 必须有：外部工具（VS Code、记事本）保存是「截断+写」，缺它会读到半截文件。

### 8.3 索引重建期间的读写一致性

用**不可变快照 + 指针切换**，不加锁：

1. `IndexService.snapshot()` 返回只读引用 `S0`；所有查询拿 `S0` 本地完成。
2. 重建在 Worker 里产出新 `S1`（新 MiniSearch 实例 + 新向量数组），**不触碰 `S0`**。
3. 完成后主进程一次赋值 `current = S1`（JS 单线程赋值即原子），`S0` 交给 GC。
4. 重建期间查询返回 `stale:true` + `lastBuiltAt`，UI 顶部显示「索引更新中」，结果照常可用（旧索引亦正确，只是不含新内容）。
5. 重建期间的增量事件进入 `pendingOps` 队列，`S1` 完成后按序重放，再切指针——避免「重建刚好漏掉落盘中的新笔记」。

并发闸门：同一时刻只允许一个 `jobId` 在跑，第二个 `rebuild` 返回 `QN_E_INDEX_BUILDING`。

### 8.4 单实例

```ts
if (!app.requestSingleInstanceLock()) { app.quit(); process.exit(0) }
app.on('second-instance', (_e, argv) => {
  if (argv.includes('--hidden')) return;      // 自启重复不弹面板
  panelWindow.ensureVisible();                // 唤出已有面板（FR-2.4）

```

`--hidden` 语义（FR-2.5）：只起球与托盘，不 `show` 面板；连球也可选不显示（设置项 `ball.visibleOnAutostart`，默认 true）。

## 9. 网络边界与隐私（承接 NFR-5）

本应用默认**零联网**。所有笔记、索引、配置、草稿均在本机磁盘，不上传、不采集、不遥测。

### 9.1 唯一出网点

| 场景 | 目标 | 时机 | 用户可见性 |
|------|------|------|-----------|
| 模型下载 | `modelscope.cn`（主）/ `hf-mirror.com`（备） | 仅当用户主动点「下载模型」 | 显式进度条 + 取消按钮 |

除上表外，代码中**不得出现任何其他 `http(s)` 请求**：不含崩溃上报、不含更新检查、不含使用统计、不含 CDN 字体（字体随包内置）。

### 9.2 实现约束

1. **统一出口**：进程内所有出网必须经 `services/net/egress.ts` 单一函数，该函数内置域名白名单常量 `ALLOWED_HOSTS = ['modelscope.cn','www.modelscope.cn','hf-mirror.com']`；非白名单直接抛错并记日志（不含 URL query，防泄漏）。
2. **禁隐式网络**：主进程启动时对 `electron.net` 与 Node `http/https` 的 `request` 打补丁，命中非白名单即拒绝并计数；计数在开发构建下断言为 0。
3. **渲染进程禁网**：CSP 已限定 `connect-src 'none'`（除本地 asset 协议），渲染层无任何 fetch 能力。
4. **内核级关闭**：`app.commandLine.appendSwitch('disable-features', 'OptimizationHints,Translate,MediaRouter')`，关闭 Chromium 的后台联网特性（拼写、翻译、投屏发现）。
5. **AI 全离线**：推理在本地 Worker 内完成，模型文件本地加载，运行期无任何网络访问（模型下载与推理是彻底分离的两个阶段）。

### 9.3 验证方法（可复现）

- **静态**：CI 中 `grep -rnE "https?://" src/` 只允许命中白名单与注释/文档链接，命中其他域名即失败。
- **动态**：启动后挂系统级抓包（或内置 egress 计数器导出），正常使用 30 分钟（编写/搜索/切目录/AI 推理）应为 **0 次外发**；仅点「下载模型」时出现对白名单域名的请求。
- **审计留痕**：`logs/egress.log` 记录每次出网的 `host + bytes + code`，**不记录 URL query 与内容**（与 04 §12 的日志纪律一致）。

### 9.4 已知例外

- 无代码签名下的 SmartScreen 提示由**操作系统**发起（非应用进程），不属应用联网行为。
- 用户手动把笔记目录放在 OneDrive/网络盘时，同步由云客户端完成，应用本身不发起同步请求。

## 10. 错误处理与降级

### 9.1 分类与反馈路径

| 类别 | 典型错误码 | 语义 | UI 反馈路径 | 用户动作 |
|---|---|---|---|---|
| **可恢复** | `QN_E_FILE_LOCKED`、`QN_E_IO`（瞬时）、`QN_E_AI_TIMEOUT`、`QN_E_AI_BUSY`、`QN_E_CANCELLED`、`QN_E_INDEX_BUILDING` | 重试或等待即可 | 状态栏/toast，**不弹模态**，3s 自动消失，附「重试」；AI 类在浮层内显示并保留原文 | 重试 / 忽略 |
| **需用户处置** | `QN_E_HASH_CONFLICT`、`QN_E_NAME_CONFLICT`、`QN_E_MODEL_MISSING`、`QN_E_MODEL_HASH`、`QN_E_PERMISSION`、`QN_E_PATH_OUTSIDE_ROOT`、热键冲突 | 必须人决策 | 面板内**非阻塞横幅**或行内错误（如重命名框下红字）；说明「发生了什么 + 建议动作 + 目标路径」 | 三选一 / 换名 / 手动下载 |
| **致命** | Worker 崩溃、`illegal instruction`、Vulkan 崩溃、主进程未捕获异常、`QN_E_UNSUPPORTED`（内存硬门禁） | 功能整块不可用 | `sys:fatal` 事件 → 全局面板页（非模态弹窗）；AI 类则**只置灰 AI 区**并写明原因（FR-7.6） | 重启应用 / 关闭 AI |

**降级阶梯**（自上而下逐级掉，任一级可用即停）：GPU 推理 → 纯 CPU 推理 → 更小模型档 → 语义检索关闭（仅词法）→ AI 全关（笔记功能 100% 可用）。**笔记主链路永不受 AI 影响**：`AiService` 在 `ipc` 层被隔离为独立 handler 组，其异常不改变其它组的注册状态。

### 9.2 日志

```
%APPDATA%\QuickNotes\logs\
├─ main-YYYYMMDD.log     主进程（含 ipc 入参摘要、错误栈、耗时打点）
├─ worker-YYYYMMDD.log   Index/AI Worker（Worker 经 postMessage 转发，不直写文件）
└─ renderer-YYYYMMDD.log 渲染进程异常（仅 error 级，经 IPC 汇入主进程统一写）
```

- 格式：`<ISO时间> <level> <module> <msg> kv...`（JSON 行可选，默认可读行），**不记录笔记正文**，只记 `id`/`len`/`hash` 前 8 位（NFR-4/5）。
- 轮转：单文件 5MB × 保留 5 份 × 按日切；超限即滚动删除最旧。启动时异步清理 7 天前日志。
- 落盘策略：`logger` 内存环形缓冲 + 每 500ms 批量 append，避免高频 fsync 拖慢主进程；崩溃时缓冲会丢最多 500ms —— 可接受，因为崩溃点由 `render-process-gone` / `uncaughtException` 单独同步落一条。
- 用户可见：设置-关于页「打开日志目录」（`qn:sys:open-path{target:'log'}`）。

### 9.3 崩溃后恢复草稿

1. **编辑器侧**：触发时机为「面板失焦收起 / 每 30s / 保存失败兜底」三者之一（写前再 800ms 防抖），直接把快照写 `%APPDATA%\QuickNotes\drafts\<sha1(相对路径)[:16]>.json`（`{ path, content, baseMtime, cursor:{line,ch}, savedAt, appVersion }`）。保存成功即删；份数 >50 按 `savedAt` FIFO 淘汰；`savedAt` 超 7 天启动时清；`editor.crashingDraft=false` 可完全关闭。
2. **启动侧**：打开某笔记时惰性检查其 `drafts\` 条目：若 `savedAt > mtime` 且 `content ≠ 磁盘内容` → 提示「检测到未保存的编辑，恢复 / 丢弃」；**绝不自动覆盖磁盘**。切换目录不删草稿（相对路径仍可解析）。
3. **渲染进程崩溃**：`render-process-gone` → 记录 reason → 若 `crashed` 则 `webContents.reload()`（最多 3 次，60s 内）；面板重载后经 main 侧 `drafts` 取回内容。
4. **主进程崩溃**：Electron 无法自愈；`uncaughtException` 时同步写日志 + 尽力 `flushAll` + `dialog.showErrorBox`（唯一允许的系统弹窗），然后 `app.exit(1)`。

## 12. 性能预算与达成手段

| 指标 | 预算 | 达成手段 |
|---|---|---|
| 冷启动到球可见 ≤3s（NFR-1） | 实测目标 0.9–1.4s | ① 球窗口用原生 DOM 不用 React（省 ~180ms 解析+挂载）② 面板窗口**不在启动路径**（首次点击才 create）③ 索引反序列化、目录扫描、硬件探测延后 1500ms 且 `setImmediate` 分批 ④ `electron-vite` 生产模式 `external` 掉 `node-llama-cpp`/`chokidar`（不参与 bundle）⑤ 不 `await` 任何磁盘操作再 `show`：先 `ready-to-show` 就显，配置读取并行 |
| 空闲内存 ≤300MB（NFR-2） | 空闲（面板关闭）≈215–265MB | ① 面板窗口闲置 10min `destroy()`，再次点击重建（+450ms，可接受）② 不用 React DevTools/Spellcheck（`spellcheck:false`）③ 索引常驻 Worker 而非主进程（不可回收的堆隔离在可 `terminate` 的线程）④ 关闭 AI 时 `worker.terminate()` 全量回收（0.6B + KV 缓存约 1.1GB 立即归还）⑤ 图标用 ico 多尺寸，不加载大图 |
| 预览渲染 ≤120ms（FR-3.2） | 常规文档 20–60ms | ① markdown-it 极简插件集（不用 highlight.js，代码块用 CSS 变色）② 输入 50ms 防抖 + 按「变更块」增量重渲（对比上一棵 AST 的顶层 block 级 diff）③ DOMPurify 只净化变更片段（全量净化在 8k 字文档约 30ms）④ 预览 DOM 用 `content-visibility:auto` 跳视口外布局⑤ 重活（大文档 >30k 字）走「预览降级为分段渲染」 |
| 搜索查询 <1ms（FR-6.2） | 1000 篇实测 <1ms | ① 索引全在 Index Worker 内存（构建 1.1–1.7s，落盘 ~4.5MB，启动反序列化 ~25ms）② 查询只回 ≤50 条并**在主进程补齐元数据**（避免整条目反序列化）③ `Intl.Segmenter` 分词预算内（Node 24 原生）④ 结果列表虚拟滚动，不为每条做 DOM |

## 13. 风险与技术债

| # | 风险 | 检测方法 | 对策 |
|---|---|---|---|
| R1 | `@node-llama-cpp/win-x64` 缺 `ggml-cpu-x64.dll` 基线变体 → 老 CPU `illegal instruction` | 打包后脚本遍历 `app.asar.unpacked/node_modules/@node-llama-cpp/win-x64/`，断言存在 `ggml-cpu-*.dll` 含无 AVX512 的基线版；CI 与真机各跑一次 | 缺失则按需求 §6 预案换 llama-server sidecar（`ai-worker.ts` 内部替换，IPC 契约不变）；同时 `hardware-probe` 在无 AVX2 机器上直接禁用 AI 并说明 |
| R2 | `asarUnpack` 漏配 → 原生模块 `MODULE_NOT_FOUND`，AI 全功能失效 | 打包产物解包后启动一次真实 AI 调用（不只看窗口起来）；关于页显示 DLL 清单 | 打包脚本内置「产物自检」：解压 `app.asar.unpacked` 断言关键路径存在，失败即构建失败（fail-closed） |
| R3 | Intel 核显 Vulkan 崩溃/负优化 | `hardware-probe` 白名单 + 首推 8s 超时 + tok/s 与 CPU 基线比对 | 默认 `ai.gpuPolicy='off'`；Intel 永不放行；回滚后写 `gpuPolicy='cpu'` + `ai.lastError`，7 天内不再尝试 |
| R4 | 4GB 机器强行开 AI → 整机页面文件抖动 | `os.totalmem()<8GB` 硬门禁；安装后首次启动即判定并置灰 | 门禁结论写入 settings（含 reason 文案），设置项禁用而非隐藏（用户能看懂为什么） |
| R5 | Worker 传输 token 过频导致 UI 掉帧 | 性能打点：`ai:chunk` 每秒事件数（目标 ≤42/s）、渲染端每帧 merge | 合帧（8 token 或 24ms）；渲染端用 `requestAnimationFrame` 批量追加，不 per-token `setState` |
| R6 | 自动保存与外部编辑互相覆盖（数据丢失） | 单测覆盖「外部改 + 本地脏」三选路径；实机用 VS Code 同时改同一文件 | `baseHash` 冲突检测 + 绝不静默覆盖 + `drafts/` 快照（§9.3） |
| R7 | chokidar 4.0.3 在大量文件/网络盘上事件风暴 | 1000 文件基准：`awaitWriteFinish` 开启后统计 10s 内事件数与主进程 CPU | `ignoreInitial:true`、批量 300ms 合并、忽略 `node_modules/.trash/assets/.*`；网络盘（UNC）检测到则降级为 30s 轮询并提示 |
| R8 | 中文分词质量不足 → 检索命中差（需求 §6 已列） | 固定 30 条查询语料的人工命中率评测（含成语、中英混排、数字） | v1 保 `Intl.Segmenter` + 词法；语义 Tab 兜底召回；失败路径记录到日志供 v2 换方案（拼音首字母/自定义词典） |
| R9 | 索引文件与笔记目录不一致（用户手工删笔记、外部批量重命名） | 启动时抽样 20 条比对 `mtime+size`；不一致计数写日志 | mtime 驱动增量 + 定期（每日首次启动）轻量校验；不一致超阈值自动全量重建（在 Worker，不阻塞） |
| R10 | 无签名 + portable 被 SmartScreen/杀软误杀 | 每次发版在干净 Win11 虚拟机走一遍下载-运行-安装；记录拦截情况 | 文档明示已知限制；提供 portable 与 NSIS 双通道；不投毒式绕过；上报误杀（提交厂商误报） |
| R11 | 双窗口失焦逻辑互相打断（点球关面板） | 手动用例：面板展开时点球、拖球、Alt+Tab 切换 | 面板 `blur` 事件 300ms 延迟 + 主进程判定焦点是否转移到球窗口（`BrowserWindow.getFocusedWindow()`），是则保持展开（实现 FR-1.5 的语义） |
| R12 | 技术债：`Result<T,E>` 与异常混用 | ESLint 规则：`services/` 内禁 `throw`（除 `QnError` 构造）；code review 门禁 | 统一 `Result`：只有 `core/errors` 允许构造错误，`ipc/register.ts` 是唯一异常→`Result` 的转换点 |
| R13 | 技术债：`shared/contracts` 与 `preload` 类型漂移（改了 DTO 忘了 preload） | `tsc --noEmit` 在 CI 必跑；preload 的 `QnApi` 由 `shared/contracts` 推导而非手写第二份 | `QnApi` 定义为 `typeof import('./api').api`，DTO 单向来源；通道名常量与 `ipc-channels.ts` 用 `as const` 双向约束 |

**已知技术债（有意接受，记录在案）**：① 无自动更新（无签名前提下的正确取舍）；② 面板窗口销毁/重建带来 ~450ms 二次展开延迟（换内存达标）；③ 向量索引全量重算成本高（换模型档位时），暂不做增量重嵌；④ `.trash` 无自动清理（v1 不做，避免误删）。
